# Five dependency findings: remediation and production triage

## Patch scope

`next` and `eslint-config-next`: 15.5.21 -> 15.5.24; `sharp` override: 0.35.3 -> 0.35.5; `source-map-js@<1.2.2` override: 1.2.2. The lock was regenerated by pnpm 10.28.0 with lifecycle scripts disabled, then checked with frozen-lockfile. No authentication, quota, database-schema or production deployment change is included.

The temporary, branch-scoped dependency-generation workflow was removed after it committed the two dependency files. No persistent write-enabled repair workflow remains in the PR tree. Original CI and vulnerability gate permissions and policy are unchanged.

Five scanner records are not five independent exploit chains or evidence of compromise. The repository Dockerfile uses Alpine Linux and an unprivileged runtime user. Actual production OS, image digest, native library build, mounts, permissions and exposure must still be inspected. A low-risk assessment for one platform is not a justification to retain known-vulnerable packages.

## Regression protections

`Dockerfile` runs the dependency-checker Node tests, then builds the application. In the final standalone image it runs `scripts/check-runtime-dependencies.mjs` as the runtime user. The checker rejects old nested copies of the three packages, validates the active Next.js/sharp resolutions and the loaded libheif/librsvg versions, and processes only an internally generated 2x2 PNG into a 1x1 WebP. There are no exploit payloads. The version floors address the named findings only and do not certify that no future vulnerabilities exist. Trivy is not disabled, suppressed or configured to ignore unfixed findings.

Run this checker only in a trusted build or isolated examination environment: loading a library in a suspected-compromised service may execute tampered code. This is a build regression check, not an intrusion detector.

## Production investigation requirements

Use three separate assessments for each running service: vulnerable version present; reachable exploitation prerequisites; evidence of exploitation/compromise. Record an evidence-confidence level and missing logs. Never equate a clean scan with proof of no previous intrusion, or an internet probe/HTTP 500 with successful RCE.

Inventory the actual running process/container/Pod and all replicas, image ID/digest, deployment start/rebuild times, filesystem OS, libc, Node runtime and source/dependency metadata. Redact secrets and subscription tokens; do not dump environment variables or application database rows. Examine proxy/WAF/application/auth/container/platform logs with a bounded time range, including rotated logs. Correlate suspicious requests with crashes, process ancestry, outbound connections, file changes, new accounts and persistence. Treat generic IOC matches as leads, not conclusive proof.

Preserve evidence before rebooting, deleting files or upgrading a suspect service. Use trusted tools, record timestamps/timezones and hashes, and retain access-restricted originals. Do not fetch suspicious URLs, render unknown images, execute downloaded scripts or launch exploit/DoS payloads against production. If high-confidence intrusion evidence appears, report it promptly and propose scoped isolation and clean-image recovery; obtain operator approval for service-affecting actions and secret rotation. Rebuild from a trusted baseline and revalidate every replica after approved deployment.
